## 1. 概要

Issue #14（AWSアカウントを本番アカウント1つに統合する）の対応の一部として、本番アカウント直下に
IAM Access Analyzer（アカウントタイプ）・Budgets・SNS通知・EventBridgeを構築する。

本番アカウントがまだAWS Organizationsのメンバーである間は、Terraform Cloudワークスペースの
認証情報（管理アカウント）から`OrganizationAccountAccessRole`へassume_roleすることで、
本番アカウント直下にリソースを構築する（[基本設計書 2.4.1](../【AWS組織管理】基本設計書.md#241-本番アカウント移行期の認証一時的な措置)参照）。
CloudTrailはデフォルトのEvent history（直近90日）を利用する方針のため、本手順の対象外とする。

IAM Identity Center（アカウントインスタンス）の新規構築・ログイン確認はIssue #14の別手順で
実施済み、または別途実施するものとし、本手順の対象外とする。

## 2. 前提条件

- 本番アカウントがAWS Organizationsのメンバーであり、`OrganizationAccountAccessRole`が
  存在すること
- Terraform Cloudワークスペース（`aws-mgmt-cmn`）のOIDC連携が管理アカウントに対して有効であること

## 3. 手順

### 3.1. Terraformコードの静的検証

```bash
cd terraform
terraform fmt -recursive
terraform validate
```

### 3.2. Terraform Cloudワークスペース変数の設定

ワークスペース変数に本番アカウントIDを設定する（Terraform変数 `production_account_id`）。

### 3.3. Terraform Cloudでのplan確認

本PRをGitHubにプッシュすると、Terraform CloudのVCS-driven WorkflowによりPlanが実行される。
以下の内容がPlan結果に含まれることを確認する。

- 追加: `aws_accessanalyzer_analyzer.accessanaly_production`、
  `aws_sns_topic.sns_topic_system_production`一式、`aws_budgets_budget.total_production`、
  `aws_cloudwatch_event_rule.evbrule_*_production`一式
- 削除・変更: なし（既存の管理アカウント側リソースへの影響はない想定）
- `assume_role`が失敗する場合、`OrganizationAccountAccessRole`の存在・信頼関係を確認する

### 3.4. apply

Plan結果に想定外の削除・変更が含まれないことを確認したうえで、PRをマージしTerraform Cloud上で
applyを実行する。

### 3.5. 動作確認

- 本番アカウントのマネジメントコンソールで、Access Analyzer・Budgets・SNSトピック・
  EventBridgeルールが作成されていることを確認する
- SNSのメール購読を承認し、通知が届く状態にする
